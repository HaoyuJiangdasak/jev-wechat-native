**2. CoAdd 实参槽已经恢复，完整 C++ 签名尚未恢复**

| 槽位 | 当前撤回提示分支的值 | 证据与限定 |
| --- | --- | --- |
| RCX / arg1 | 外层服务对象 `[outer_this+0xC80]` | `0x180e36b` 读取，之后传递；具体 C++ 类型及所有权未知 |
| RDX / arg2 | 可写的 16 字节结果容器地址 | CoAdd 保存该指针，向其写入两项/16 字节；wrapper 用它提取消息并释放共享控制块 |
| R8 / arg3 | 完整消息对象地址 | outer 的 R8 保存后拆成两半 XOR；inner `0x3965efd..0x3965f18` 还原指针 |
| R9 / arg4 | 消息中的一个 32 字节字符串对象地址 | 由 `0xA54240(message)` 选择；CoAdd 首先检查 `[R9+0x10]` 字符串长度；推断为会话对端标识 |
| arg5 | byte `0` | inner 在 CALL 前写 `[rsp+0x20]=0`，CoAdd 的入口栈槽为 `[entry_rsp+0x28]` |
| arg6 | byte `1` | inner 在 CALL 前写 `[rsp+0x28]=1`，CoAdd 的入口栈槽为 `[entry_rsp+0x30]` |
| RAX 返回 | 结果容器指针 | wrapper 返回其输入 output 指针；不能把它解释为整数成功码 |

在 CoAdd prologue 中压入 8 个寄存器，再减 `0x668`，然后 `RBP=RSP+0x80`，所以 `RBP=entry_rsp-0x628`。`0x3893f02` 读取 `[rbp+0x658]` 是 **arg6**；`0x3894ef9` 读取 `[rbp+0x650]` 是 **arg5**。arg6 与消息 `+0x148` 是否为零共同控制分支，arg5 被拷入后续闭包对象；仅凭历史“允许新 ID”注释，不能给当前两个 bool 都套上确定名称。

对照：旧分支 inner `0x3893da0` 将 arg5 和 arg6 都置 1。两者确实不同，不能简单选首次命中。

**4. 生命周期和后处理**

- `0x180e350` 在 CoAdd 返回后调用 `0x17c4b50`，后者复制共享结果并增引用、调用 `0x39ce60` / `0x39f570`，比较类型信息后用 `0x1C42E0` 将消息复制到外层输出；不匹配路径进入异常相关调用。结果很像携带已完成或待完成状态的类型擦除共享对象，但未确认其 C++ 类型，不能直接宣称为某种 `std::future`。
- `0x3933030` 先调用 `0x1C42E0` 复制消息，再分配 `0x300` 字节，将消息通过 `0x1569FA0` 移入分配区 `+8`，用 `0x1C50F0` 析构临时对象，最后调用 `0x39E6F0` 设置共享结果。多处控制块 `+8` / `+0xC` 的原子增减和虚函数回收都必须保持成对。
- CoAdd 的一般路径把 peer 字符串、arg5 和共享存储状态捕获到 `0x3933D50` 构造的环境，复制消息后调用 `0x2F9A550`。这是可继续追踪调度/执行上下文的具体入口；目前不能推断它可在任意外部线程直接执行。
- origin 在 `0x234eb3a` 调用 `0x15819B0`，该函数释放目标字符串、移动源字符串并把源 size 清零、capacity 重置为 15。**这是消息 move-assignment 后处理，不是已找到的 UI refresh。** 随后 `0x234eb47` 调用 `0x1C50F0` 析构返回的临时消息。

对应证据：`storage-wrapper-0x17c4b50.asm.txt`、`storage-wrapper-0x3933030.asm.txt`、`storage-wrapper-0x3933d50.asm.txt`、`storage-wrapper-0x15819b0.asm.txt`，以及三个 `storage-wrapper-0x2350*.asm.txt`。

**5. 下一步静态验证应解决的具体缺口**

1. 从 origin 中 `[rbp+0x2B8]` 消息的首次定义向上追到真正的默认/系统消息构造，并对照 `0x1C42E0`、`0x1569FA0`、`0x1C50F0` 恢复所有拥有资源的字段；确定会话 ID、SrvID、时间、type、正文/XML 的合法组合。aixed 的发送对象不是这里的消息类型。
2. 顺着 `0x47220 -> 0x36C740 -> 0x6F4520` 的服务访问链和 `outer_this+0xC80` 核实服务生命周期；沿 `0x2F9A550` 及共享结果函数核实执行线程、调度和错误传播。单纯传一个地址不能满足这些依赖。
3. 沿入库完成后的回调/事件路径核实聊天模型通知及屏幕重绘。既有公开 BetterWX 的“重新进入聊天才显示”说明入库与刷新必须分别测试。
4. 找到独立构造路径后仍须确认没有发送分发/网络提交调用。当前局部 CoAdd 链属于撤回本地存储流程，**不足以证明任意未来适配器完整调用链永不外发**。

静态辅助脚本 `dump_storage_wrappers.py` 每次核对 DLL SHA-256，用 PE `.pdata` 确定函数边界，默认导出正确两个 wrapper 和 peer 选择函数；仅读取磁盘文件。以上结果是具体、可复核的适配研究进展，不是已完成的原生功能。
